## Added
- **Perforce, built in.** termide carries a Perforce plugin: no Python, no download, the same on Linux, macOS and Windows; `p4` on `PATH` is all it needs. It sleeps until the global config gives it a mode (`[plugins.perforce]` with `mode = "on"`, or `"opt-in"` and `enabled = true` in a project's file), so a repository alone never wakes it, and it stays a process of its own that starts only in a project that wants it. It shows the state of the file in the editor in the status bar (`p4: #3/5 (out of date)`, `edit · change 1234`, `locked by …`), opens it for edit when `Ctrl+E` turns editing on in the read-only file, asking first when someone else has it open (or for add from the palette), offers to revert it when `Ctrl+E` turns editing back off, and asks then whether to save or discard unsaved changes, lists the opened files by changelist, in a tree of folders, on `Alt+G` in a project outside git, where `Enter` opens a file, `F3` shows its diff in the git diff panel, `Backspace` reverts it, `Space` lists what can be done with it and `Enter` on a changelist submits it — the default changelist from a dialog with its description and the files to go, shows the file's diff from the palette, syncs in a terminal, and gives the agent `opened`, `diff` and `edit` tools. It colours the opened files in the file manager and marks the lines changed against the depot in the editor's gutter, as termide does for git. A plugin of the same name in the plugins directory takes its place.
- **Plugins can show another version control's state.** `files/status` colours files in the file manager in git's colours (`modified`, `added`, `deleted`, `ignored`), the directories above a changed file included, and `editor/base` gives the text the editor marks changed lines against. `file/will_edit` hands `Ctrl+E` on a file that is read-only on disk, and back off on a saved writable one, to the plugins first, so one can check the file out or revert it, and have unsaved work saved or discarded, instead of the editor overriding the permission. A command with `"replaces": "open_git_status"` runs on `Alt+G` in a project outside git. Git comes first in both: they fill in only where git has nothing to say, such as outside a repository. A plugin's panel may be a `list` instead of Markdown: groups of rows with the actions on each, moved through and run with git status's keys, rows with a path in a tree of folders, and buttons under them; or a `diff`, a unified diff shown as the git diff panel shows git's. `window/dialog` asks in one window put together from a message, a text field of one or several lines, a list to read, pick from or tick, and up to six buttons.
- **API keys in the password vault.** A connection's page in the AI settings has an **API key** field: the key typed there, masked, goes into the encrypted vault under the connection's name, never into `config.toml`, and the field shows only whether one is stored. A variable named by `api_key_env` still comes first. A request whose key is in a locked vault asks for the master password; cancelled, it fails saying so. Renaming a connection moves its key, deleting it removes the key. A key pasted into `api_key_env` instead of a variable name is shown as `********` with a warning, and one choice in the **API key** field moves it into the vault. A run from the command line cannot unlock the vault and needs `api_key_env`.
- **Who spent a session's tokens.** The agent panel's session info (`F3`, `/usage`) breaks the session's tokens down by who spent them — the conversation, subagents, the `auto` reviewer, `recall`'s solver, summaries, the `/goal` judge, `/handoff`, and what Claude Code spends inside itself on its own subagents, summaries and helper calls — and by model — a subagent's read from its own session log, its reviewer included — each with a bar and its share of the tokens, every kind counted as one, with the share of prompt tokens the cache served and, where the provider counts it apart (Codex, OpenAI-compatible servers), the output spent reasoning. It also shows what the context is made of — system prompt, tool definitions, skills, tool output, conversation, summary, and what a CLI agent holds of its own beyond them — and each tool's results across the session, a skill's by name: what they brought into the context and how much the model calls after them read again. The figures come from the session log, so a reopened session shows them, and the status bar's totals start from what the session had spent instead of from zero; a fork counts from its own start.

## Fixed
- **A reopened agent session shows how full its context is.** Reopening a session, or restarting termide, put its context at 0 until the next reply, however much it held since its last summary; a Claude Code or Codex session's fill and window are now kept in its log, and the built-in agent's read from its last call.
- **A reopened agent session shows its whole conversation.** Reopening a session, or restarting termide, showed only what its last compaction left in the context — the summary posing as your first message and the few messages kept — though the live panel had shown everything and the log kept it all. The panel now shows every block on the branch, with the compaction's notice where it happened, as the run showed it; the model's context is unchanged.
- **A Claude Code or Codex reviewer's tokens are counted.** The `auto` mode reviewer, `recall`'s solver and the goal judge asked of Claude Code or Codex reported nothing spent, so the session's totals left them out — about a third of the Claude Code spend termide drove. They now count, credited to the model the call ran on, a call the agent stopped or refused included.
- **Leaving edit mode asks about unsaved changes.** `Ctrl+E` or a click on `Edit: Yes` in a text editor with unsaved changes switched to viewing and kept them in the buffer, and in the hex editor the edits stayed pending out of sight, so closing the view later could lose them without a word. Both now ask first: save and view, discard the changes and view, or cancel and keep editing.
- **An open file follows its write permission.** A file opened without write permission stayed read-only in the editor after `p4 edit` or a `chmod +w` made it writable, until `Ctrl+E` or reopening it — the first thing a Perforce user hits, since Perforce keeps files read-only until they are checked out. The editor now looks at the permission again when the file changes on disk and when a collapsed panel is shown: writable makes it editable, read-only again (`p4 revert`) makes it read-only, except over unsaved work. `Ctrl+E` still overrides the mode until the permission changes next, and a file opened to view only stays read-only.
- **The `p4 edit` example in the custom commands documentation** bound `Alt+E`, which opens a new editor, so its command never ran from the keyboard; it binds `Shift+F5` now.
